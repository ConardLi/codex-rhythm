# 我做了一个小工具，让 Codex 的 5 小时倒计时提前跑起来

Codex 5 小时额度限制恢复后，新一轮倒计时不会立刻开始，而是要等你再次使用 Codex 才会触发。

这件事平时不太容易察觉，但真正连续使用时就会很明显。比如早上额度已经恢复，我一直没有打开 Codex；下午两点开始工作，五小时窗口也从下午两点才开始计算。如果一个小时内把额度用完，下一轮仍然要等到晚上才能恢复。

换句话说，明明上午有一大段不用 Codex 的时间，却没有被算进重置周期。

于是我做了一个 macOS 菜单栏小工具：**Codex Rhythm**。

它做的事情很直接：观察当前 Codex 额度。如果确认 5 小时计时还没有真正开始，就发送一次受保护的 Codex 请求，让这一轮倒计时提前运行。这样，当我真正坐下来工作时，当前周期可能已经走了两三个小时，而不是刚刚开始。

## 不是简单地“每隔十分钟发一句话”

最初看起来，这个工具似乎只需要一个定时任务：每隔一段时间调用一次 Codex 就行。

实际做起来没这么简单。

首先，它不能在已经计时的时候继续发送请求，否则只是在白白消耗额度。其次，额度接口在使用量为 0% 时，也可能返回一个“约五小时后”的时间。这个时间会随着每次刷新不断向后移动，它看起来像重置时间，实际上只是占位值。

如果只判断“有没有未来的重置时间”，程序就会误以为窗口已经启动，真正需要发送请求时反而什么也不做。

Codex Rhythm 因此不会只看一个时间字段。它会综合判断：

- 当前数据是否刚刚来自官方额度接口；
- 5 小时使用量是否已经发生变化；
- 重置时间是否在多次检查中保持稳定；
- 一周剩余额度是否高于保护线；
- 当前是否处于用户设定的检查时段；
- 本轮是否已经触发过，或者正在冷却与重试。

只有这些条件成立，它才会执行动作。

## 两种使用方式

我把操作方式尽量压缩成了两种，不要求用户理解复杂的自动化概念。

第一种叫“自动守候”。用户可以设置每天的使用时段，例如 08:00 到 23:00，再选择每 5、10、15 或 30 分钟检查一次。程序只检查额度状态，不会每次都调用 Codex；只有确认当前没有真实计时窗口时，才发送一次请求。

第二种叫“固定时间”。例如每天 08:30 检查一次，也可以增加第二个时间。这种方式更适合使用节奏稳定的人。

除此之外，还有一个“手动启动计时”按钮。想立即开始当前周期时，不需要修改任何规则，直接点击即可。

## 请求成功，不等于计时成功

这个工具有一个我比较在意的设计：它不会因为命令执行成功，就直接告诉用户“计时已经开始”。

Codex CLI 返回结果后，程序会继续轮询官方额度状态。只要观察到使用量增加，就可以确认窗口已经生效；如果请求非常小，使用量仍然显示为 0%，程序则要求连续三次读到稳定的重置时间，并且这个时间需要落在五小时上下十分钟的合理范围内。

也就是说，界面上看到的“已确认启动”不是乐观提示，而是经过二次验收的结果。

## 顺手看清自己的额度节奏

除了自动启动，Codex Rhythm 也承担了一个更日常的功能：把额度状态放到菜单栏里。

打开控制中心，可以看到：

- 5 小时剩余额度；
- 本轮还有多久重置；
- 一周剩余额度与重置时间；
- 可用的限额重置次数；
- 计时助手当前状态；
- 下一次自动检查时间。

我还增加了一个“时间预测”。它会以当前已经确认的重置时间为起点，推算未来三轮大概会在几点恢复。例如本轮 18:16 重置，后面两轮就预计是 23:16 和第二天 04:16。

这里显示的是预测，不是服务端承诺。如果电脑休眠、网络中断、程序没有运行，或者下一轮没有及时触发，实际时间就会向后顺延。

## 一个克制的本地工具

Codex Rhythm 使用原生 SwiftUI 和 AppKit 编写，没有 Electron，也没有第三方运行时依赖。

额度查询需要读取本机已有的 Codex 登录信息。访问令牌只在内存中使用，只发送到 `chatgpt.com` 的相关接口，不会写入项目日志。程序没有统计分析、广告、崩溃上报，也没有自己的服务器。

计时助手默认关闭。只有用户主动开启，或点击手动按钮时，程序才会运行本机的 Codex CLI。可用限额重置也不会自动消耗，每次都必须由用户确认。

## 它不能保证什么

这个工具并不能创造更多额度，也不是绕过限制的方法。它只是尝试更合理地安排已有的重置周期。

即使要求模型只回复几个字，一次真实 Codex 请求仍然可能包含系统上下文，所以不能把它理解为零成本操作。Codex 的额度计算方式、窗口行为和相关接口也可能变化，工具需要持续跟进兼容性。

因此，我更愿意把它叫作“额度与计时助手”，而不是某种额度破解工具。

## 为什么决定开源

这类工具会接触本机登录信息，也会执行 Codex CLI。与其只提供一个来历不明的安装包，我更希望把读取范围、网络请求、触发条件和确认逻辑全部公开，让使用者能够自己检查、自己编译。

开源以后，我也希望它能继续保持三个原则：

1. 功能直观，不要求用户学习复杂概念；
2. 自动操作必须保守，并且结果可以验证；
3. 数据处理尽量留在本地，不增加不必要的服务。

如果你也经常遇到“真正开始工作时，五小时倒计时才刚启动”的情况，Codex Rhythm 或许能让你的使用节奏更舒服一点。
